## M. The mode-scoping map — which application reads each lockdown key

Placed ahead of §A because it governs §B and §E rather than living inside either. Three separate
blockers were raised against one section of `configure/authentication` — `API_ENABLED`,
`AUTH_REQUIRED`, `AUTH_SIGNUP` — and all three were the same defect: a key was described by its
*stated* effect, and the stated effect is wider than its reader. The root cause is structural. These
keys are read by the **Core web app**; full mode routes the equivalent surface through the **Auth
app** (Rodauth), which never consults them. A page author who checks a row here does not have to
re-derive that, and the fourth instance does not get written.

**How to read the rows.** Each row fixes four things: the reader(s) at `4cbd42149`, the routes
actually gated, **what happens in full mode**, and whether the SPA is the only consumer (which makes
the key a UI gate, not a control). Where full mode makes a key inert, that is the row's headline,
not a footnote.

## G. Security headers

**The shape to write the page around:** exactly one header is a config toggle owned by OTS (CSP,
on/off). Six more are on/off toggles over `Rack::Protection` middleware. The header *values* —
CSP directives, HSTS max-age, referrer policy — are owned by the `otto` and `rack-protection`
gems and are **not configurable from OTS config**.

**Two emitters, not one — read §G.4 before writing any absence into this page.** The Ruby
application is only the first emitter. `etc/examples/Caddyfile-example` carries a response-header
block that sets five security headers, two caching headers and a robots header on every response,
and it is not merely an example: `docker/variants/caddy.dockerfile:123` bakes it into the
`onetimesecret-caddy` image as `/etc/caddy/Caddyfile`, and `docker/compose/docker-compose.full.yml:52`
mounts it read-only into the `proxy` service. So every operator running the documented full stack
gets it, and two of its values **differ from what the app sends**. Rows G9, G10, G14 and G16 state
what the *Ruby* side does; each is now paired with the proxy fact. A claim of absence whose search
covered only `lib/` and Ruby under `apps/` is not an absence claim about the deployment.

**And four application-layer emitters, not three — read §G.6 before writing any absence into this
page.** G28 enumerated three: `otto`'s per-route header set, the `Rack::Protection` components the
`site.middleware.*` toggles govern, and Core's CSP middleware. It missed a fourth. The Auth app
declares six `Rack::Protection` mounts of its own in its application class, inside an
`Onetime.production?` block, and one of them is `ContentSecurityPolicy` — so a full-mode production
instance emits a second, one-directive CSP under `/auth` that `CSP_ENABLED` cannot switch off, and
runs two protections there (`HttpOrigin`, `IPSpoofing`) whose `site.middleware.*` toggles ship OFF.
Rows G29–G32. The same rule as above applies with the search path changed: a claim of absence whose
search covered `lib/` and `apps/web/core/` is not a claim about `apps/web/auth/`.

## H. Open questions — stop and ask rather than infer

1. **Organizations in simple mode (B9).** `registry.rb:157-165` skips only `web/auth/` and
   `web/billing/`, so the organizations API loads in simple mode, and `ENABLE_ORGS` carries no
   auth-mode gate. Whether the org UI is *usable* there is still unsettled. The published page
   that used to claim full-mode-only was rewritten and now says nothing about organizations, so
   there is no longer a contradiction to reconcile — only a gap. Settling it needs a runtime
   check (boot simple mode, `ENABLE_ORGS=true`, hit the org endpoints), not another read. Until
   then `configure/authentication` must not assert either way.
2. **`Permissions-Policy` on the wire (G16, G16a).** Still open, and G16a was rewritten this pass
   so it no longer claims otherwise. The app sends no header and the meta tag is inert; the
   shipped proxy config *declares* an empty-valued one, and the file evidence establishes that the
   line is a set rather than a removal (removals in the same block use a `-` prefix). What is not
   established is how Caddy renders a set-to-empty-string value — an empty-valued header on the
   wire, or nothing at all. Nothing in this repository settles it and no test here asserts it. The
   policy effect is nil either way, so `configure/security-headers` can be written without waiting
   on this, in the form G16a gives. Capture two responses — one through the full stack, one direct
   to the app — before stating anything narrower.
3. **Emitted CSP in production** — G4's directive list is the gem's source. A live capture would
   confirm no intermediary rewrites it. Same class of gap the Phase-2 ledger flagged for
   `Cache-Control`.
4. **`site.authentication.colonels` (B29).** Code reads it; nothing writes it and no env var
   feeds it. Is it a live-but-undocumented knob or dead code? Worth an app-repo issue rather than
   a docs decision.
5. ~~**`AUTH_SIGNUP` in full mode (B39).**~~ **Closed by M8.** It did not need a runtime check after
   all; it needed the enablement site. Rodauth's `create_account` feature is enabled with no
   predicate (`account_management.rb:9`), in the same method where `verify_account` *is* wrapped in
   a config check — so `AUTH_SIGNUP=false` leaves `POST /auth/create-account` serving in full mode.
   B39 is superseded: cite **M8**, not B39, and state the per-mode split rather than avoiding it.

## Do not claim

- **"Enable the SSO entitlement" / "SSO requires an upgraded plan" on any operator page.**
  `manage_sso` is in `STANDALONE_ENTITLEMENTS` (`with_plan_entitlements.rb:55`), so on a stock
  self-hosted install it is already granted. The string "SSO management requires the manage_sso
  entitlement. Please upgrade your plan." (`apps/api/domains/logic/sso_config/base.rb:34`) is the
  hosted-tier message. Self-hosted, the real gates are `AUTH_SSO_ENABLED`, full mode, provider
  credentials, and — for the per-domain surface — `ORGS_SSO_ENABLED` plus org ownership.
- **Any per-page statement that entitlements or limits are something the operator configures.**
  There is no config key that sets an entitlement list. Row 0.4.
- **"Set `OIDC_REDIRECT_URI` to your callback URL."** No code reads it (C8). Tell the operator to
  register `https://<host>/auth/sso/<route-name>/callback` **at the IdP** and note the app derives
  its own value from the request host.
- **"Full mode requires PostgreSQL and RabbitMQ."** SQLite is the shipped auth-database default
  (B7) and jobs ship disabled with a synchronous fallback (B8). Say what each service buys, not
  that it is required.
- **"There are three authentication modes."** Two (B2). `AUTHENTICATION_MODE=disabled` silently
  gives you simple mode; disabling auth is `AUTH_ENABLED=false`, a different key.
- **"Secrets are capped at 30 days."** Not at HEAD. The absolute bound is 365 days
  (`MAX_TTL`); the practical ceiling is the `ttl_options` maximum, which ships at 30 days but is
  operator-settable. Row E9 — and correct the Phase-2 ledger row 29 rather than copying it.
  **But do not write the flat "there is no 30-day cap" either**: API v1 keeps its own hardcoded
  `V1_MAX_TTL` of 30 days and a 60-second floor, and clamps silently (M19, M20). State the ceiling
  per API version.
- **"HSTS max-age is configurable in OTS config."** It is not. `MIDDLEWARE_STRICT_TRANSPORT` is
  on/off only; the one-year value with no `includeSubDomains` and no `preload` comes from
  `rack-protection` (G10). Same for `X-Frame-Options`' `SAMEORIGIN` (G9) and the referrer policy
  (G14). **But do not write the flat "it is not configurable" either** — the shipped proxy config
  already overrides `X-Frame-Options` to `DENY` and the referrer policy to `no-referrer`, and
  carries a commented HSTS override (G9, G10, G14a, G19). The honest form is: no OTS key sets
  these values; the edge does, and the shipped edge config already changes two of them.
- **"No `Permissions-Policy` is sent."** Not established, in either direction. The app sends none
  and the meta tag is inert, but the shipped proxy config declares an empty-valued one, and what
  Caddy emits for that is open (G16, G16a, §H item 2). Say what each layer *declares*, not what
  arrives at the browser.
- **"`AUTH_SIGNUP=false` stops new accounts."** Only in simple mode. In full mode — which the full
  Compose stack defaults to — Rodauth serves `POST /auth/create-account` and enables `create_account`
  unconditionally; the only server-side gate on that setting is a Core handler the Auth app shadows
  (M8). Same for **"`AUTH_SIGNIN=false` closes sign-in"** (M9). In full mode both are UI gates.
- **"`API_ENABLED=false` returns 404 for `/api/*`."** Nothing server-side reads the key; the API apps
  mount and serve regardless, and the only consumer is a notice in the SPA's account settings page
  (M14). The defaults file's own comment states the 404 behaviour, and the comment is wrong — do not
  quote it.
- **Any lockdown instruction that lists `site.authentication` keys without naming the mode.** In full
  mode only `AUTH_ENABLED` binds on the auth endpoints (M16). A checklist that reads the same in both
  modes is wrong in one of them.
- **"Paid plans are exempt from the v1 rate limits."** Not usable language for a self-hoster: the
  guard reduces to "authenticated with an API token", and a stock self-hosted install has no plan
  tiers at all (M18, row 0.4). Write the exemption in terms of authentication, not billing.
- **"`AUTH_REQUIRED=true` locks the instance down."** It is a UI gate on the canonical homepage
  and nothing else; no server-side code reads it (B42). A lockdown page that lists it as an access
  control is wrong.
- **"`API_GUEST_ROUTES_ENABLED=false` stops anonymous secret creation."** It does not close API
  v1, which mounts unconditionally, accepts anonymous callers on `share`/`generate`/`create` and
  the receipt routes, and never calls the guest-route gate (E31, E27). Any lockdown instruction
  built on the guest-route switches must name v1 explicitly.
- **"Configure `TRUSTED_PROXY_MODE` / `TRUSTED_PROXY_CIDRS` for your proxy."** Not on their own —
  the master switch ships **off** and the whole block is inert until `TRUSTED_PROXY_ENABLED=true`
  (B41). Every client-IP claim on an operator page (admin CIDR allowlist, IP rate limits) inherits
  that default.
- **"A failed email is retried."** Only inside the RabbitMQ `EmailWorker`, and only for a
  *transient* classification; jobs ship disabled and the fallback paths carry no retry at all
  (D7, D7a). Also note `:unknown` counts as non-transient.
- **"With `EMAILER_MODE=disabled` you just don't get email."** On the shipped `AUTH_AUTOVERIFY=false`
  it also means no new account can ever sign in, and the app logs nothing about it because the
  no-op backend reports success (D34).
- **Any header claim sourced from a search of `lib/` and Ruby under `apps/` alone.** §G.4 is the
  second emitter. Search `etc/`, `docker/` and the `.rue` templates before asserting an absence.
- **"Configure the Content-Security-Policy directives."** OTS exposes `CSP_ENABLED` and nothing
  else; the directive set is `otto`'s (G4). The single exception is `form-action`, widened
  automatically by SSO (G5) and by `SSO_FORM_ACTION_ORIGINS`.
- **"CSP violations are reported to …"** Reporting is never enabled (G6).
- **"Set a cookie domain."** There is no such option (F10).
- **"Set `session.secure` to match your TLS setup."** It is derived. Writing the key at all can
  make a production deploy *worse* than leaving it absent (F9). Tell the operator to set `SSL` /
  `site.ssl`, or rely on `RACK_ENV=production`.
- **"`SECRET` must be at least N characters / must be hex."** No such requirement exists (A4).
  Recommend `rake ots:secrets` and its 64 random bytes; do not invent a rule the code does not
  enforce.
- **"Changing `SECRET` is safe if you keep a backup."** Changing it under existing data makes
  pre-rotation ciphertext unreadable until it is restored or `SECRET_PREVIOUS` carries the old
  value (A14/A19). The verifier only *detects* this, and only warns by default (A16).
- **"Set `emailer.from` — optional."** It is the one email value with a placeholder default that
  nothing validates (D9). Treat it as required.
- **"The app sends a `Permissions-Policy` header."** It does not. A `<meta http-equiv>` tag
  exists in the head template, but `Permissions-Policy` is header-only and browsers ignore the
  meta form, so the app restricts nothing and there is no OTS knob (G16). Four ways to get this
  wrong, all to be avoided: claiming the app sets a policy; claiming the template is empty of it
  (the tag is there and a reader will find it); claiming no `Permissions-Policy` exists anywhere
  (the shipped proxy config declares one, with an empty value); and claiming a full-stack operator
  receives one on the wire (open — G16a).
- **Anything about what onetimesecret.com has configured.** Every value here comes from
  `etc/defaults/`. There is no production config in this repo.
- **Any plan-tier, seat or price statement.** Hard stop per the billing gate, unchanged.
